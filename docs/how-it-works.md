# Как это устроено: путь от PDF до ответа

Документ для того, чтобы рассказывать вслух. Каждый шаг: что на входе, что делаем, что на выходе, почему именно так.

Конвейер разделён на две части. **Подготовка** идёт один раз офлайн и кладёт результат на диск. **Ответ** читает готовое и не открывает PDF вообще — во время демонстрации файл не трогается ни разу.

```
ПОДГОТОВКА (один раз)                    ОТВЕТ (на каждый вопрос)
PDF                                      вопрос
 ├─ закладки  → sections.json             ├─ роутер по оглавлению ──┐
 ├─ таблицы   ─┐                          ├─ или BM25 по чанкам ────┤
 └─ vision    ─┴→ tables_merged.json      └─ или всё целиком ───────┤
                  → aggregates.json                                 ↓
                                                          сборка контекста
                                                                    ↓
                                                                 модель
                                                                    ↓
                                              цитаты · проверка чисел · границы
                                                                    ↓
                                                                 ответ
```

# Часть 1. Подготовка

## Шаг 1. PDF → разделы

**Вход:** `data/yandex_annual_report_2025.pdf`, 201 страница.

**Что делаем.** Не парсим оглавление и не угадываем заголовки по кеглю. Берём **встроенные закладки** документа — те самые, что показывает панель навигации в любой читалке. Автор отчёта уже разметил структуру, и это готовая смысловая разметка, которую остаётся только прочитать: `fitz.open(pdf).get_toc()`.

В отчёте 178 закладок: 9 верхнего уровня, 33 второго, остальные глубже.

Граница раздела считается так: раздел кончается на странице перед следующей закладкой **того же или более высокого уровня**. Подраздел не обрывает родителя, а следующий равноправный сосед — обрывает.

**Выход:** `data/sections.json`, по записи на закладку:

```json
{
  "id": "s118-ключевые-риски-компании-и-управление-ими",
  "title": "Ключевые риски компании и управление ими",
  "level": 4,
  "page_from": 119,
  "page_to": 121,
  "text": "…текст страниц 119-121 целиком…"
}
```

**Почему так.** Раздел — это смысловая единица, а не кусок фиксированной длины. Внутри раздела таблица не разрывается пополам, потому что резать по количеству символов мы вообще не начинаем.

**Где ломается.** У PDF без закладок весь документ возвращается одним разделом. Экономные режимы при этом вырождаются в полный контекст. Это записано в контракте и в списке отложенного.

## Шаг 2. PDF → числа, два независимых пути

Это самая содержательная часть, и на защите её стоит рассказывать подробно.

### Путь А: код

Сначала `pdfplumber` по страницам с табличной сеткой, затем координатный разбор для графиков, у которых подписи лежат в текстовом слое: берём тик оси года и ближайшую по горизонтали подпись значения.

Дал 266 записей с 26 страниц.

### Путь Б: зрение

Каждая из 201 страницы рендерится в PNG при 200 dpi и уходит в модель с задачей: вернуть все числовые данные страницы — из таблиц, графиков, диаграмм, выносок. Ответ строго в JSON, номер страницы дописывается кодом, а не спрашивается у модели.

Дал 866 записей с 99 страниц. Стоимость прохода 8,47 доллара, результат закэширован постранично.

### Почему двух путей мало, а одного недостаточно

Числовые данные в отчёте лежат в трёх видах:

| Вид | Берётся | Записей |
|---|---|---|
| таблицы с сеткой | кодом | 113 |
| графики с текстовым слоем | кодом, по координатам | 92 |
| **графики-растры** | **только зрением** | **61** |

Ключевые сегментные графики — страницы 87, 89, 90, 91, 94, 96, 97 — это картинки. `get_text()` отдаёт по ним ноль. И вот главное: **парсер при этом не падает**. Он молча возвращает пусто, система отвечает на остальные вопросы и выглядит исправной, а сегментная выручка тихо исчезает из данных.

Отсюда правило, которое стоит произнести: проверять надо не наличие текстового слоя в документе, а происхождение каждого числа.

### Сверка двух путей

Там, где оба пути дали значение для одной комбинации «метрика + сегмент + период + страница», значения сравниваются. Совпало — запись помечается подтверждённой. Разошлось — флаг.

Результат: 264 подтверждено, расхождений ноль, только код 2, только зрение 602.

Три оговорки, которые надо называть самому: ноль получен после доводки правил сопоставления по первым шести несовпадениям; часть сравниваемых записей на первом проходе была снята вручную; 602 записи вторым источником не проверены вовсе.

## Шаг 3. Нормализация чисел

Выполняется **до** попадания в JSON, иначе арифметика поедет молча.

| Что в документе | Что делаем | Почему |
|---|---|---|
| `(1 234,5)` | `-1234.5` | в финотчётности скобки означают минус, а не группировку |
| `1 441,1` с неразрывным пробелом | `1441.1` | четыре вида пробелов служат разделителями тысяч |
| `12,3` | `12.3` | запятая десятичная |
| `269,7¹` | `269.7` | сноска отрезается **до** нормализации Unicode, иначе надстрочная единица приклеится к значению |
| `1 441,1 млрд руб.` | `1441.1` + единица `млрд_руб` | единица живёт в шапке таблицы, а не в ячейке |
| `—`, `н/д`, пусто | записи нет | пустая ячейка не ноль |

## Шаг 4. Запись числа

Каждая ячейка становится **отдельной записью**, а не строкой таблицы. Это длинный формат:

```json
{"t":"seg_rev","m":"Выручка","s":"Городские сервисы","p":"2025",
 "v":804.5,"u":"млрд_руб","pg":21,"src":"both","confirmed":true}
```

- `t` — идентификатор таблицы или графика
- `m` — метрика, `s` — сегмент или строка (может быть пустым)
- `p` — период, `v` — значение числом, `u` — единица
- `pg` — **страница**, `src` — откуда (`parser` / `vision` / `both`)

**Зачем разворачивать.** В Markdown-таблице модель сама сопоставляет строку с колонкой, и на отчёте, где рядом стоят 2024 и 2025, она может съехать на соседний год. Здесь съехать некуда: у каждой ячейки свой период и своя единица прямо в записи.

**Провенанс структурный.** Поле `pg` означает, что источник любого поданного числа известен. Не надо просить модель «указывай страницу» и надеяться — страница уже лежит рядом со значением.

**Цена.** Длинный формат кратно тяжелее исходной таблицы: 30 на 6 в Markdown это около 600 токенов, развёрнутый — около 2700. Поэтому ключи короткие, а в контекст блок подаётся с фильтрацией (шаг 8).

## Шаг 5. Агрегаты

Считает **код**, не модель. Из `tables_merged.json` строится `aggregates.json`:

- прирост абсолютный и в процентах год к году,
- доля сегмента в консолидированной выручке,
- **вклад в прирост** — сколько процентов общего прироста дал каждый блок.

Последнее отвечает на вопрос «почему прибыль выросла сильнее выручки»: там нужна раскладка по драйверам, а не одно число.

При выборе значения из нескольких кандидатов работает правило доверия: запись, подтверждённая двумя путями, выигрывает у неподтверждённой, а более точная — у округлённой. Именно так 1441,1 из финансового раздела побеждает 1441,0 из обзорной врезки.

**Зачем.** Системный промпт запрещает модели считать в уме, но запрет работает только если посчитанное уже подано. Иначе она посчитает сама — и, как показал замер, действительно считает.

## Шаг 6. Контрольная сумма

Сумма выручки шести верхних блоков сверяется с консолидированным итогом.

На реальных данных: сумма блоков 1630,9 против итога 1441,1, расхождение 13,17%. Разбор показал, что это не ошибка разбора — сноски на страницах 21 и 87 говорят, что блоковая выручка приведена **до** коррекции на межсегментные расчёты в 189,7 млрд. С коррекцией 1441,2 против 1441,1, расхождение 0,007%.

Механизм поймал расхождение и потребовал объяснения. Без него данные выглядели бы правдоподобно и были бы неверны на 13%.

**Границы контроля, которые надо назвать честно:** покрыта одна метрика одного периода; поправка берётся из тех же разобранных данных, поэтому ошибка в самой строке межсегментных расчётов сверкой не ловится; порог 0,5% выбран рабочим, а не выведен.

# Часть 2. Ответ на вопрос

## Шаг 7. Выбор данных: три стратегии

### Полный контекст

Все девять разделов верхнего уровня в промпт. Ничего не теряется, платим 206 тысяч токенов и два доллара за вопрос.

### Роутер по разделам

Модели подаётся **только оглавление**: 178 заголовков со страницами, около 4 тысяч токенов. Она возвращает строгий JSON:

```json
{"sections": ["s118-ключевые-риски…"], "confidence": 0.9, "need_full": false}
```

Правила разбора ответа:

- идентификаторы, которых нет в документе, отбрасываются — модель иногда придумывает;
- пустой выбор или неразобранный ответ означают «нужен весь документ», а не «отвечай наугад»;
- уверенность ниже порога **расширяет** набор родительскими разделами, а не сужает: лишний раздел стоит копейки, потерянный стоит неверного ответа;
- флаг `need_full` модель ставит сама на широких вопросах, и это штатное поведение.

Важная деталь, которая стоила промаха на первом прогоне: оглавление подаётся до **четвёртого** уровня. Раздел «Ключевые риски компании и управление ими» — заголовок четвёртого уровня, и на мелком оглавлении роутер физически не мог его выбрать. Глубина стоит 3 тысячи токенов и снимает слепую зону.

### Лексический поиск

Документ режется на чанки, дальше BM25.

**Как чанкуем.** Берутся **листовые** разделы — те, внутри которых нет вложенных. Родитель отбрасывается, потому что его текст уже содержится в детях, и подача обоих удваивает контекст. Раздел длиннее 6000 символов режется по абзацам с перекрытием 400 символов, чтобы факт на границе не потерялся между кусками. Получилось 145 чанков, средний размер 2650 символов.

**Что переносим из метаданных в текст — и зачем.** У чанка есть поля `section_title`, `page_from`, `page_to`. Но индексируется не голый текст, а склейка:

```
Ключевые риски компании и управление ими
стр. 119-121
…текст чанка…
```

Заголовок и диапазон страниц физически кладутся **внутрь** индексируемой строки. Причина простая: запрос «риски» должен находить раздел, в заголовке которого стоит это слово, даже если в теле оно встречается редко. Метаданные лежат в стороне от индекса и на ранжирование не влияют — их надо занести в текст, иначе они для поиска не существуют.

**Почему BM25, а не эмбеддинги.** Финансовый отчёт состоит из чисел и точных терминов, а плотные эмбеддинги на них слабее лексического поиска: «1441,1» и «1441,2» для эмбеддинга почти одно и то же, для BM25 — разные токены. Плюс BM25 работает локально, без вызова модели и без денег. Точка подключения плотной ветки оставлена в модуле.

**Параметры:** k1 = 1.5, b = 0.75, выдача top-8. Восемь, а не три, намеренно: при узкой выборке проигрыш ветки объяснялся бы размером окна, а не качеством поиска, и замер потерял бы смысл.

## Шаг 8. Сборка контекста

Промпт собирается из трёх частей:

```xml
<question>Какая была выручка компании в 2025 году?</question>

<numbers>
{"numbers":[{"t":"main_fin","m":"Выручка","p":"2025","v":1441.1,"u":"млрд_руб","pg":86}, …],
 "aggregates":{…приросты, доли, вклад в прирост…}}
</numbers>

<document>
<section id="s101-финансовые-результаты" title="Финансовые результаты" pages="86-97">
…текст раздела как есть…
</section>
</document>
```

**Почему текст в XML, а числа в JSON.** Это не эстетика, а два разных требования.

Длинный текст внутри JSON-строки нужно экранировать: кавычки, переносы, слэши. На реальном документе это стабильный источник поломок. В XML-теге текст лежит как есть, ничего не экранируется.

Атрибуты тега дают атрибуцию бесплатно: модель берёт `pages="86-97"` из разметки, а не выдумывает номер.

Числа наоборот: JSON компактнее (нет закрывающих тегов на каждой ячейке), это родной формат для структурированного вывода, и он читается pandas и DuckDB без конвертации.

Итого: контейнер XML, данные внутри JSON.

**Что подаётся всегда, а что по выбору.** Блок чисел с агрегатами идёт в контекст при **любом** режиме — он компактный и нужен почти каждому вопросу. Роутер и лексический поиск выбирают только текстовые разделы.

**Фильтрация чисел.** В экономных режимах сырые записи фильтруются по страницам выбранных разделов, иначе 868 записей съедают всю экономию. Плюс всегда добавляются якорные страницы 21 и 12 — там сводная таблица сегментов и ключевые показатели, нужные почти любому числовому вопросу.

**Дедупликация разделов.** Если выбраны и родитель, и вложенные разделы, вложенные выбрасываются: их текст уже внутри родителя. Без этого шага контекст раздувался до 251 тысячи токенов — больше, чем весь документ.

## Шаг 9. Правила для модели

Системный промпт задаёт пять правил, нарушение любого делает ответ негодным:

1. Отвечать только по поданному контексту, знания о компании из других источников не использовать.
2. Каждое число сопровождать номером страницы в формате `(стр. N)`.
3. Если данных нет — сказать это и назвать, чего именно не хватает; не достраивать по смыслу.
4. Не пересчитывать в уме то, что подано готовым в блоке агрегатов.
5. Отвечать коротко, по-русски, без вводных оборотов.

Правила — это просьба, а не гарантия. Поэтому дальше идут проверки.

## Шаг 10. Что делается с готовым ответом

### Извлечение цитат

Из текста вынимаются все `стр. N` — это список страниц, на которые ответ сослался. Он показывается пользователю и участвует в оценке замера.

### Проверка чисел

Из ответа вынимаются все числа и каждое ищется в поданном контексте. Не нашлось — флаг.

Механика, в которой пришлось повозиться:

- сравниваются **значения**, а не написание: `1 441,1`, `1441.1` и `1441,1` это одно число;
- допуск — половина единицы последнего разряда, поэтому округление модели выдумкой не считается: написала 35,8 там, где в контексте 35,76 — права;
- сравнение через `round()` не годится: `round(61.15, 1)` в Python даёт 61.1, потому что 61.15 не представимо в двоичном формате точно. Работает сравнение по допуску;
- пробел считается разделителем тысяч только перед ровно тремя цифрами. Без этого «2025 4 582,5» склеивалось в 20254582,5, и проверка сама порождала несуществующее число;
- ссылки на страницы, включая диапазоны, вырезаются до разбора, иначе хвост «-88» из «стр. 86-88» становился отдельным числом;
- числа в диапазоне 1900–2099 исключаются как годы. Оговорка: под это правило попадают и настоящие величины из этого диапазона, они не проверяются.

Проверка работает: замер поймал, что модель приводит вычисленные ею проценты, которых в источнике нет. Проверено вручную — значения 39,6 и 56,2 отсутствуют в контексте при любом способе разбора.

### Границы ответственности, два рубежа

**Первый — по вопросу.** Список формулировок вида «стоит ли инвестировать», «рекомендуете покупать», «should I invest». Список конечен, и перефразированный вопрос его обходит — это надо говорить прямо.

**Второй — по ответу.** Детектор вердикта в готовом тексте: «рекомендую покупать», «акции стоит купить», «однозначно покупать». Срабатывает независимо от того, как был задан вопрос. При срабатывании ответ помечается предупреждением сверху и блоком о границах снизу. Текст модели при этом не редактируется и не подавляется — пользователь видит и его, и пометку.

Собственный блок о границах детектор на себя не поднимает, отрицания вроде «не рекомендую покупать без анализа» тоже не ловит.

## Шаг 11. Что получает пользователь

```
Answer:
  text                — ответ, при срабатывании границ с пометками
  cited_pages         — [12, 21, 86]
  section_ids         — какие разделы были поданы
  unverified_numbers  — числа без подтверждения в контексте
  verdict_leaked      — сработал ли второй рубеж
  mode                — режим поиска, включая случай падения в полный
  prompt_tokens       — сколько потрачено
  latency_s           — сколько ждали
  cost_usd            — сколько стоило
```

В интерфейсе: ответ, четыре метрики, раскрывающийся блок с источниками и списком поданных разделов. Числа без подтверждения показываются предупреждением, а не замалчиваются.

# Три вещи, которые связывают всё вместе

**Провенанс встроен в структуру, а не выпрошен промптом.** Страница лежит в записи числа и в атрибуте тега раздела. Модель не может привести поданное число «ниоткуда», потому что источник приходит вместе со значением.

**Арифметика в коде, формулировка в модели.** Приросты, доли и вклад в прирост считает pandas, модель получает готовое и складывает из него текст. Там, где она всё-таки считает сама, это видно по флагу непроверенного числа.

**Два независимых пути к одному значению превращают тихий отказ в шумный.** Код против зрения при разборе, сумма частей против итога при агрегации, число ответа против числа контекста при выдаче. Везде, где можно получить величину дважды, она получается дважды.
