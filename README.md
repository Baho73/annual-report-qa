# AI-ассистент по годовому отчёту

Отвечает на вопросы по годовому отчёту публичной компании со ссылкой на страницу источника. Документ: Годовой отчёт МКПАО «Яндекс» за 2025 год, 201 страница, [ir.yandex.ru](https://ir.yandex.ru/MKPAO/issuer-report).

Тестовое задание, ограничение 1–2 часа. Оценивается качество инженерных решений, а не объём функциональности, поэтому здесь подробно описано, что сделано, что сделано не было и почему.

## Запуск

```bash
pip install -r requirements.txt
export OPENROUTER_API_KEY=...

python -m report_qa.parse      # подготовка: PDF → sections.json + tables.json (один раз)
streamlit run app.py           # демо
python eval/run_eval.py        # прогон замера
```

Подготовка вынесена из времени ответа сознательно: во время демонстрации PDF не открывается ни разу.

## Архитектура в пяти строках

1. **Разделы** — PDF режется по встроенным закладкам документа (178 штук, 9 верхнего уровня). Автор отчёта уже разметил структуру, парсер оглавления не нужен.
2. **Числа** — таблицы разворачиваются в длинный формат, одна запись на ячейку, с номером страницы внутри записи. Модель физически не может привести число без источника.
3. **Арифметика** — приросты, доли и вклад в прирост считает pandas. Модель формулирует вывод, а не умножает.
4. **Маршрутизация** — роутер читает оглавление (2–3k токенов) и решает, какие разделы подать. В большую модель уходит 7–15k вместо 175k.
5. **Границы** — на запрос инвестиционной рекомендации выдаются факторы за и против с цифрами, вердикт «покупать» не выдаётся никогда.

## Экономика: почему дешевле не значит выгоднее

Цена ошибки в этой задаче несоизмерима с ценой токенов, и это меняет всю логику оптимизации.

**Доверие нелинейно.** Ассистент с точностью 99 процентов и ассистент со 100 отличаются не на процент, а качественно. После первой пойманной ошибки пользователь обязан перепроверять каждый ответ, а если он всё равно перепроверяет, продукт не экономит ему ничего. Одна ошибка обесценивает сотню верных ответов, потому что убивает режим работы «доверяю и не проверяю».

**Экономия живёт не там, где её ищут.** Считаем на реальных цифрах:

| Статья | Стоимость |
|---|---|
| Вопрос на топовой модели, полный контекст | ~150 руб (~$1.8) |
| Тот же вопрос в режиме `router` | ~10 руб |
| Перепроверка одного ответа аналитиком (открыть PDF, найти таблицу, сверить) | 250–800 руб (5–10 мин при ставке 3–5 тыс/час) |

Перепроверка дороже самого ответа в два-пять раз. Значит экономия на классе модели, добавляющая хоть немного перепроверки, отрицательна по деньгам даже тогда, когда счёт за токены уменьшился.

**Отсюда правило, а не компромисс.** Снижение класса модели — обмен качества на деньги, и в задаче, где ошибка дороже токенов, этот обмен убыточен. Сокращение контекста — не обмен: выкидывая из промпта разделы, не относящиеся к вопросу, мы одновременно платим меньше и повышаем шанс попасть в нужный факт.

Стоимость продукта снижается за счёт повышения его качества, а не против него. Убираем шум — получаем и точность, и экономию одним движением. Ход, который улучшает качество, применяется без ограничений; ход, который его ухудшает, — только до порога, где метрики ещё держатся, и порог этот определяется замером, а не ощущением.

## Матрица замера: режим × модель

Главный вопрос защиты — «почему выбран такой стек». Он закрывается не рассуждением, а прогоном одного набора из десяти вопросов через все комбинации.

**Режимы поиска**

| id | Что делает | Токенов на вопрос |
|---|---|---|
| `full` | документ целиком в контекст | ~175 000 |
| `router` | роутер выбирает разделы по оглавлению | 7 000 – 15 000 |
| `vector` | чанки по разделам, эмбеддинги, top-8 | ~6 000 |

**Модели** (цены OpenRouter на 2026-08-12, вход/выход за миллион токенов)

| id | Окно | Цена | Расчётная цена вопроса в режиме `full` |
|---|---|---|---|
| `claude-opus-5-fast` | 1000k | 10 / 50 | ~$1.80 |
| `claude-fable-5` | 1000k | 10 / 50 | ~$1.80 |
| `gpt-5.5-pro` | 1050k | 30 / 180 | ~$5.40 |
| `gpt-5.2-pro` | 400k | 21 / 168 | ~$3.90 |
| `claude-opus-4.1` | 200k | 15 / 75 | ~$2.60, окно впритык |

**Матрица результатов** — заполняется прогоном `eval/run_eval.py`, значения подставляются автоматически из `eval/results.json`. Цифры сюда попадают только из прогона; расчётные оценки живут отдельно и помечены как расчётные.

Ещё не измерено. Запустите `python eval/run_eval.py --modes router,full`.
<!-- MATRIX:END -->

**Как читать матрицу.** Движение вправо удешевляет за счёт класса модели и бьёт по качеству напрямую. Движение вниз удешевляет за счёт объёма контекста, и по проверяемой гипотезе качество при этом не падает, а растёт: на контексте за сотню тысяч токенов модели хуже находят факт в середине. Поэтому порядок оптимизации такой — сначала вниз, потом вправо, и останавливаемся там, где метрики перестают держаться.

Полный прогон в режиме `full` на топовой модели стоит около 50 долларов за десять вопросов. Для теста приемлемо, для продукта нет — это и есть содержание вывода.

## Тест-матрица вопросов

Пять вопросов задания — не список примеров, а проверка разных слоёв системы. Ещё пять добавлены для покрытия отказов.

| Вопрос | Тип | Что ломает | Раздел |
|---|---|---|---|
| Выручка в X году | точечный факт из таблицы | чанкинг рвёт число от периода в соседней колонке | Финансовые результаты, 86–97 |
| Что росло быстрее, с цифрами | агрегация + арифметика | LLM считает приросты в уме с ошибками | Финрезультаты, сегменты 90–96 |
| Основные риски | нарратив | риски раскиданы, страдает полнота | Корпоративное управление, 103–125 |
| Почему прибыль обогнала выручку | multi-hop, причинность | top-k собирает куски из разных мест | Финрезультаты + Приложения |
| Стоит ли инвестировать | граница ответственности | модель охотно выдаёт финансовый совет | почти весь документ |
| Риски на отчётности МСФО | **проверка на честность** | модель дописывает известное ей про компанию | ответа в документе нет |

Последняя строка — главный тест. В консолидированной отчётности по МСФО бизнес-рисков не бывает, там раскрыты только валютный, кредитный и риск ликвидности. Модель с претрейном охотно допишет конкуренцию и регулирование, и внешне это будет выглядеть хорошим ответом. Правильное поведение: перечислить раскрытое и назвать границу документа.

## Обработка документа

| Этап | Решение | Почему так |
|---|---|---|
| Разбор PDF | PyMuPDF, закладки документа | у отчёта готовая иерархия из 178 закладок |
| Таблицы | второй проход pdfplumber | fitz отдаёт таблицу плоским текстом |
| **Графики-картинки** | **vision-проход по 7 страницам** | **см. ниже: 23% чисел не извлекаются кодом вообще** |
| Числа | нормализация до попадания в JSON | `(1 234)` это минус, разделитель тысяч — неразрывный пробел, единица живёт в шапке, сноски липнут к значению |
| Формат | JSON для чисел, XML для текста | JSON компактнее и читается pandas; длинный текст в JSON-строке требует экранирования и ломается, в XML лежит как есть, а атрибуты тега дают атрибуцию |
| Контроль | сумма сегментов против итога | расхождение больше 0.5% означает потерянную строку или неразобранный знак. Без сверки ошибка разбора становится уверенным враньём в ответе |

### Три вида числовых данных в одном документе

Первый прогон парсера дал 266 записей из 24 таблиц на 26 страницах и вскрыл главную проблему документа:

| Вид | Как берётся | Записей |
|---|---|---|
| таблицы с сеткой | pdfplumber + координаты слов | 113 |
| графики с текстовым слоем | тик года → ближайшая по горизонтали подпись | 92 |
| **графики-растры** | текстового слоя нет; нужен vision | **61 (23%)** |

Ключевые сегментные графики — страницы 87, 89, 90, 91, 94, 96, 97 — картинки. `get_text()` на стр. 90 отдаёт по ним ноль чисел.

Опасность не в том, что данные недоступны, а в том, что **парсер не падает**. Он молча возвращает пусто, система отвечает на остальные вопросы и выглядит работающей, а сегментная выручка — ядро второго вопроса задания — тихо исчезает. Отсюда правило: проверять не наличие текстового слоя в документе, а происхождение каждого числа.

Проверка масштаба показала, что семь страниц были выборкой по факту находки, а не покрытием: **растровые объекты лежат на 74 страницах из 201**, на 51 из них занимают больше 5% площади. Поэтому vision-проход идёт по всему документу — порядка 300 тысяч токенов входа, три-пять долларов, несколько минут, один раз на этапе подготовки.

Полный проход даёт второе применение бесплатно: там, где парсер уже извлёк число, зрение работает **независимым контролёром**. Совпало — уверенность высокая, разошлось — флаг и разбор. Два независимых пути к одному значению превращают тихую ошибку разбора в шумную. Именно этот механизм поймал бы три бага, найденные ручной сверкой пяти страниц, без участия человека.

### Результат полного прогона (201 страница, $8.47)

| Источник | Записей | Страниц с числами |
|---|---|---|
| парсер | 266 | 26 |
| vision | 866 | 99 |
| объединено | 868 | 99 |

| Категория сверки | Записей |
|---|---|
| подтверждено обоими независимо | **264** |
| расхождения | **0** |
| только парсер | 2 |
| только vision | **602** |

**Парсер видел четверть источников.** Числовые данные лежат на 99 страницах из 201, код добрался до 26. Инвентарь объектов подтверждает масштаб: 112 таблиц и 46 графиков в документе против 24 таблиц, взятых парсером. Две трети итогового набора существуют только благодаря vision-проходу.

**Ноль расхождений там, где сравнивать было с чем.** 264 записи получены двумя независимыми путями и совпали, включая те 61, что раньше были зашиты в код вручную — теперь они воспроизводятся автоматически.

Оговорка о честности метрики: первые прогоны сверки показывали шесть расхождений, и все шесть оказались артефактами сопоставления, а не разногласиями в данных — стороны по-разному раскладывают текст между полями «метрика» и «сегмент». Цифра «расхождений ноль» валидна ровно настолько, насколько корректен матчер, и это надо произносить вслух, а не прятать.

Непроверенными остаются 602 записи, полученные только зрением: сверять их не с чем. Это известное ограничение, а не упущение.

### Контрольная сумма: что она поймала

Сумма по блокам дала 1630,9 против консолидированных 1441,1 — расхождение 13,17%. Разбор показал, что это не ошибка парсера: сноски на стр. 21 и 87 говорят, что блоковая выручка приведена **до коррекции на межсегментные расчёты** (189,7 млрд). С коррекцией 1441,2 против 1441,1, остаток 0,007% — округление.

Механизм отработал ровно так, как задуман: поймал расхождение и потребовал объяснения. Без него данные выглядели бы правдоподобно и были бы неверны на 13%.

Ручная сверка пяти страниц дополнительно поймала три бага парсера: слипание слов в подписях метрик, склейку двух отрицательных значений в «−8,3−5,0», неверный порядок кварталов при сортировке по вертикали вместо горизонтали. Все три ушли бы в продукт молча.

## Компромиссы

Принятые из-за ограничения по времени:

- Один документ. Мультидокументность добавила бы разбирательство, где показатель по МСФО, а где скорректированный, — на два часа это не помещается.
- Замер сокращён до десяти вопросов и трёх метрик вместо полноценного бенчмарка.
- Векторная ветка существует ради сравнения, а не как продукт: без reranker и гибридного поиска. При этом сделана добросовестно — чанки по разделам, таблица целиком, top-8. Соломенное чучело обесценило бы весь замер.
- Streamlit вместо API с фронтендом: защита это демонстрация, а не витрина интерфейса.

Не сделано, с условием включения:

| Не сделано | Когда добавить |
|---|---|
| Мультидокументность, обновление корпуса | отчётов больше одного или они обновляются |
| Reranker, гибридный поиск | векторный режим выходит из замера в продукт |
| Агент с инструментами | появляются внешние источники: котировки, отчёты конкурентов |
| История диалога, уточняющие вопросы | приходит живой пользователь вместо десяти тестовых вопросов |
| Локальная модель | появляется запрет выпускать данные наружу |
| OCR | приходит отчёт картинкой (проверено: во всех кандидатах текстовый слой есть) |
| text-to-SQL поверх DuckDB | таблицы перерастают контекст либо вопросы становятся произвольными |
